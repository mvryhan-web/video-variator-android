# Block 5 — internal ownership, queue and zero-paid-AI isolation

Code-level review of consolidated draft PR #50 (not a production release).

1. **Who can view or act:** every private `/api/product-watcher/admin/*` route uses existing authentication middleware followed by a strictly checked Google account, nonempty `ADMIN_EMAIL`, and a valid user ID. Unit tests exercise **all 11** routes against anonymous, wrong-provider, wrong-email and missing-ID users and assert zero DB access for denied requests. A Telegram chat ID alone does not convey ownership.
2. **Dedicated work/queue:** separate private `server/product-watcher/worker.js`, `PRODUCT_WATCHER_*` enable switches default OFF, owner PAUSED, four distinct PostgreSQL advisory locks and dedicated `vv_product_watcher_*` scheduling/report/review/notification tables. The single shared `vv_admin_audit` stores owner decisions. No new Customer Agent, wallet, Stripe ledger or user job queue is introduced.
3. **Zero paid model-spend entitlement:** Product Watcher has **no paid AI generation path**. No user credits are reserved, debited or refunded by Watcher, and the code does not invoke the provider router. Its telemetry reads *aggregate counts and recorded costs* from existing BASE data; the one approved billing import provides **configuration metadata only**. This avoids commingling Watcher spend with user spend; it does not claim a general-purpose future agent budget exists.
4. **Outbound resource limits:** existing health check is scheduled at most every 15 minutes, official source inspection at most three allowlisted HTTPS URLs every six hours (1 MiB each, 9s timeout), and Telegram owner notifications at most three claimed critical alerts per tick (no automatic retry on ambiguous success). Their optional feature flags are independent. Official source reading and owner notifications have network resource usage, but **not provider-credit debits**.
5. **Actual worker status:** only the worker writes a heartbeat. The web service may legitimately lack `PRODUCT_WATCHER_SCHEDULER_ENABLED`; owner panel now reports fresh DB heartbeat rather than incorrectly requiring the WEB process flag. A stale heartbeat never proves a running worker.

## How to verify

`node --test tests/product-watcher-isolation-unit.mjs tests/product-watcher-admin-unit.mjs` is run by the watcher CI in addition to the rest of the suite and isolated PostgreSQL tests. The static import/write rules detect simple unintended couplings; they are **regression guards, not a complete security audit**. Code review, actual staging permissions, real costs, worker deployment, independently verified backup/recovery, and activation remain separate gates. The production feature must remain disabled until explicitly approved. This document does not authorize Render, database migration, paid API calls or Telegram send.
